# Whole-Game Development Order

기준일: 2026-10-18  
상태: **개발 순서 기준안 — 코드 구현 및 Studio 검증 완료를 의미하지 않음**  
Source of truth: 이 문서는 게임 전체의 작업 의존성과 단계 순서를 정의한다. 공간 하나를 제작하는 세부 순서는 각 `docs/02_WORLDS/*.md`와 기능 시스템 명세를 따른다.

## 1. 개발 순서 결정 원칙

1. 먼저 실제 구현 상태를 확인한다. 코드가 있거나 UI가 보인다는 이유만으로 기능 완료로 판정하지 않는다.
2. 핵심 약속을 end-to-end vertical slice로 완성한다. Catalog 검색 → 착용 → 다른 플레이어에게 외형 표시 → 정확한 아이템 해제 → Current Outfit/Wearing 동기화 → 저장 → 재접속 복원이 한 흐름으로 작동해야 한다.
3. 공간은 일찍 전체적인 크기·연결·이동 경로를 블록아웃하되, 모든 공간을 동시에 아트 완성하지 않는다.
4. 한 번에 하나의 대표 상호작용을 구현하고 검증한 뒤 복잡도를 늘린다.
5. Runway와 Housing은 현재 핵심 흐름의 선행 조건으로 만들지 않는다.
6. UI 요구사항, 소스에 존재하는 동작, 사용자가 확인한 동작, Studio에서 검증한 결과를 구분한다.
7. 기능별 우선순위는 `GAME_MASTER.md`와 이 문서에서 관리한다. 공간별 제작 순서는 해당 공간 문서에서 관리한다.

## 2. 전체 작업 순서

### Stage 0 — 저장소와 요구사항 기준선 고정

- [ ] 현재 작업 브랜치와 실제 Rojo source 경로를 확인한다.
- [ ] `src/`의 실행 소스와 `workbench/`의 격리 작업본을 구분한다.
- [ ] Catalog, Avatar, Outfit, Save Data 문서 간 상태·용어·완료 기준을 대조한다.
- [ ] 현재 코드의 실제 기능과 미해결 문제를 `CATALOG_IMPLEMENTATION_STATUS.md`, `ISSUES.md`, `WORKLOG.md`에 분리 기록한다.
- [ ] 이 단계에서는 새 UI를 무조건 다시 만들거나 작업본을 자동으로 실행 소스에 복사하지 않는다.

**완료 조건:** 다음 작업자가 실행 소스, 작업본, 미완료 기능, 미검증 사항을 혼동하지 않는다.

### Stage 1 — Catalog 핵심 흐름을 실제 소스에서 완성

- [ ] 검색·카테고리·필터·페이지 결과가 유효한 빈 결과와 API 오류를 구분한다.
- [ ] 서버 요청에서 item type을 명시하고 Asset과 Bundle을 구분한다. Bundle ID를 Asset ID처럼 취급하지 않는다.
- [ ] 서버에서 item ID/type을 검증하고, 지원되지 않는 유형은 명확하게 거절한다.
- [ ] Wear/Remove 요청을 서버에서 직렬화하거나 중복 요청을 거절한다. 클라이언트의 로컬 busy flag만으로 서버 경쟁 상태를 방지했다고 간주하지 않는다.
- [ ] 성공 후 실제 적용된 HumanoidDescription을 다시 읽고, 요청한 변경이 반영됐는지 검증한다.
- [ ] Current Outfit, Wearing, 카드 상태와 아바타 미리보기를 하나의 서버 확인 snapshot에서 갱신한다.
- [ ] 제거는 정확한 유형/ID의 항목만 대상으로 하며, 같은 종류의 다른 항목을 제거하지 않는다.
- [ ] PC/모바일, 다른 플레이어에게 보이는 외형, respawn, 실패 응답을 Studio에서 확인한다.

**완료 조건:** 지원 유형의 검색→착용→다른 플레이어 확인→정확한 해제→UI 동기화가 반복 테스트를 통과한다. 미지원 유형은 성공처럼 표시되지 않는다.

### Stage 1.5 — Avatar Editor: 액세서리 조정 (2026-10-19 추가)

Avatar Editor는 카탈로그 안의 무료 핵심 기능이다. VIP 뒤로 미루지 않는다. 플레이어는 아이템을 입고, 위치·회전·크기를 미세 조정한 뒤, 그 결과를 Wardrobe에 저장한다. 따라서 Stage 1.5는 Stage 2보다 먼저 진행하고, Stage 1.5와 Stage 2는 한 묶음으로 검증한다.

- [ ] 기술 검증 실험(Studio): AccessoryDescription 조정값 보존, 클라이언트 미리보기 적용, GetAvatarRules의 조정 대상·범위 확인. 결과는 `docs/05_TECH/API.md`에 기록한다.
- [ ] 진입점: 최대화 상태의 미리보기 ⚙ 버튼, 최소화 상태의 탐색 띠(최근/인기/즐겨찾기/착용 중 뒤)에 ⚙ 추가. ⚙는 카탈로그를 최대화하면서 편집 모드로 연다.
- [ ] 편집 모드: 왼쪽 미리보기를 재사용한다. 오른쪽 영역에 착용 중 목록(카테고리별)과 액세서리 조정(이동/회전/크기, 축별 슬라이더·입력·재설정)을 둔다.
- [ ] draft → 적용/버리기: 적용 전에는 실제 캐릭터를 바꾸지 않는다. 적용 시 서버가 범위를 검증하고 적용 결과를 다시 읽어 확인한다.
- [ ] 기존 착용·해제 경로가 조정값을 지우지 않는다(다른 아이템 착용·해제 후에도 유지).
- [ ] 체형·피부색·레이어 순서는 지원 범위를 검증한 뒤 후속 단계로 추가한다. 검증 전에는 UI에 노출하지 않는다.

**완료 조건:** 지원되는 액세서리를 조정·적용하면 다른 플레이어에게도 보이고, 이후 다른 아이템을 착용·해제해도 조정값이 유지되며, 미지원 아이템은 이유와 함께 비활성화된다.

### Stage 2 — Wardrobe(SavedOutfits)와 영구 데이터

- [ ] 서버 권위형 appearance snapshot과 typed item identity를 정의한다.
- [ ] Favorites와 SavedOutfits의 저장 schema, 버전, migration, 데이터 크기 한도를 구현한다.
- [ ] SavedOutfits 사용자당 최대 50개를 설정값으로 관리한다. 같은 이름은 허용하되 outfitId는 고유해야 한다.
- [ ] 저장, Wardrobe 목록, 선택 복원, 이름 편집/삭제 정책, 재접속 복원을 구현한다.
- [ ] Wardrobe 진입점: 최소화 상태 탐색 띠의 ⚙ 다음에 Wardrobe 버튼. 누르면 기존 카테고리 결과 카드 영역에 "의상 저장" 카드와 저장된 의상 카드들을 보여 준다.
- [ ] 저장 snapshot에 Stage 1.5에서 적용한 액세서리 조정값을 포함하고, 복원 시 조정값까지 재적용한다.
- [ ] 미지원/삭제 항목은 해당 항목만 건너뛰고 유효 항목을 적용한다. 저장 원본을 자동 변경하지 않는다.
- [ ] 빈 Wardrobe와 로드 실패, 일시 오류와 잘못된 데이터, payload 초과와 모호한 쓰기 결과를 구분한다.
- [ ] 실제 DataStore 재접속 테스트와 schema migration fixture 테스트를 수행한다.

**완료 조건:** 저장 결과가 확인되기 전 성공을 표시하지 않고, 재접속 후 데이터가 유지되며, 부분 복원과 실패 복구가 명세대로 동작한다.

### Stage 3 — Main Social의 회색 블록아웃 (Stage 1과 병행 가능)

- [ ] Central Plaza/Spawn, 연결 도로, Club, 선택한 Photo Spot, Park/Playground, Beach, Cafe/Rooftop 후보의 대략적인 인접 관계를 정한다.
- [ ] 구역 간 이동 거리, 시야, 아바타 가시성, 경계, 카메라, PC/모바일 동선을 회색 블록아웃으로 확인한다.
- [ ] 당장 구현하지 않을 공간은 단순한 통로/표지/닫힌 입구로 표현할 수 있다. 미래 기능을 위해 완성된 건물이나 별도 Place를 만들지 않는다.
- [ ] 공간별 문서에서 미확정된 연결/외관은 확정 사항처럼 모델링하지 않는다.

**완료 조건:** 플레이어가 어디서 시작하고 어디로 이동할 수 있는지 명확하며, 핵심 공간의 상대적 위치를 바꿀 필요가 큰 구조적 문제가 발견되지 않는다.

### Stage 4 — Club MVP

- [ ] Main Social 내부의 Club 구역에서 기본 춤 선택, 시작, 종료를 구현한다.
- [ ] 다른 플레이어에게 춤과 캐릭터 움직임이 보이는지 검증한다.
- [ ] 이동/점프/respawn/카탈로그 열기와 닫기 중 애니메이션 상태가 꼬이지 않는지 확인한다.
- [ ] PC/모바일 조작과 동시에 여러 명이 이용하는 상황을 테스트한다.
- [ ] 처음부터 그룹 군무 편집기, 복잡한 DJ 시스템, 별도 Place를 만들지 않는다.

**완료 조건:** 혼자서도 즐길 수 있고 다른 플레이어의 춤을 관람할 수 있으며, 춤 시작/종료가 캐릭터를 잠그지 않는다.

### Stage 5 — 대표 Photo Spot과 사진 UX → 인생네컷 포토 부스 P1·P2 (2026-10-20 결정 제안)

2026-10-20: 사진 UX를 인생네컷 포토 부스로 만든다(`docs/01_SYSTEMS/PHOTO_BOOTH.md` §9). 부스가 카메라 구도·포즈·진입/퇴장·여러 명 사진을 모두 포함하므로 Stage 5의 대표 기능으로 삼는다. 순서: 클럽 마무리(2인·모바일) → 인생네컷 P1·P2 → VIP 혜택 정리 → 인생네컷 P3(유료 프레임·스티커) → Stage 6.


- [ ] 여러 포토존을 한 번에 만들지 말고, 서로 다른 구도를 제공하는 1~2곳부터 선택한다.
- [ ] 카메라 프레이밍, 포즈, 조명, 캐릭터 가시성, 진입/퇴장 동작을 정의한다.
- [ ] PC/모바일 카메라 조작과 다른 플레이어가 함께 있는 경우를 테스트한다.
- [ ] 사진 촬영만 포함한다. 공개 갤러리 게시·좋아요·공개 스타일 복제 피드는 범위 밖이다.

**완료 조건:** 선택한 장소들이 실제로 서로 다른 구도를 제공하고 카메라/포즈 사용 후 일반 이동으로 돌아올 수 있다.

### VIP / Monetization — 기반 기능 준비 후 별도 수직 구현

VIP 구매 기능은 Catalog 핵심 작업보다 앞서지 않으며, 모든 월드 제작이 끝날 때까지 무조건 미룰 필요도 없다. 다음 기반이 준비된 뒤 추가 시스템 작업으로 진행한다.

- Catalog 핵심 흐름과 무료 검색/미리보기/임시 착용이 안정화되어 있다.
- Main Social에서 다른 플레이어의 캐릭터 표시와 이름표 등 관련 표시를 검증할 수 있다.
- 사진 촬영 UI와 기본 포즈 흐름이 존재해 유료 포즈 묶음을 실제 경험에 연결할 수 있다.
- 서버 권위형 구매/소유권 검증과 실패 처리 원칙을 구현할 수 있다.

VIP는 Avatar Editor와 Wardrobe의 무료 기능을 막지 않는다. 기반이 갖춰지기 전에도 서버의 소유권 확인 모듈만은 다른 작업과 병행해 만들 수 있다.

구현 순서: VIP Pass 소유권 확인 → VIP 배지/추가 외곽선 → 별도 포즈 묶음 소유권 및 사용 권한 → 구매 취소·실패·재접속·respawn·다중 사용자 QA.

이 작업은 Photo Spots의 기본 카메라/포즈 UX가 검증된 뒤 진행하는 것을 기본안으로 한다. 필요한 기반이 Stage 6의 월드 제작과 병행해 준비되면 VIP 작업도 병행할 수 있다. 가격, 외곽선/포즈 수량, 배지 디자인, 실제 Roblox 상품 유형과 상품 ID는 `docs/01_SYSTEMS/MONETIZATION.md`에서 관리하며, 이 문서에는 의존성과 순서만 둔다.

**완료 조건:** VIP와 포즈 묶음의 소유권이 서로 분리되어 검증되고, 무료 Catalog/소셜/기본 포즈 기능이 유료 권한과 무관하게 정상 작동하며, 다중 사용자 표시와 구매 실패 복구가 테스트된다.

### Stage 6 — 추가 공간은 하나씩 수직 구현

다음 공간은 전부 동시에 만들지 않는다. 플레이테스트와 제작 비용에 따라 순서를 다시 선택할 수 있다.

1. **Beach + Dream Aquarium:** 해변 휴식 상호작용 하나, 돔에서 수중 공간으로 나가 수면과 해변으로 돌아오는 경로를 먼저 검증한다. 수중 체류 제한은 프로토타입 결과에 따라 결정한다.
2. **Cafe / City View:** 앉기와 전망/창가 사진 구도부터 검증한다. 카페는 **Glasshouse Cafe 한 곳**에서 앉기·주문·음료 제공을 검증한 뒤 Hanok Cafe·Sunset Beach Cafe로 외관만 바꿔 확장한다 (CAFE.md §8, D-072). 카페 알바를 넣기로 하면 **이 카페 상호작용 검증 단계에서 함께 설계**한다 (CAFE.md §9, 현재 기획만·구현 보류).
3. **Fantasy Playground:** 그네 하나의 탑승/애니메이션/하차를 먼저 검증한다. 회전목마, 바이킹형 놀이기구, 롤러코스터는 각각 별도 복잡도 검토 후 추가한다. (2026-10-22: 사용자 요청으로 관람차·회전목마·그네·흔들 그네·미끄럼틀 회색 박스 + 기능 구현, PARK.md §8.)
4. **Central Street / decorative landmarks:** 연결과 탐색을 돕는 장식부터 추가한다. 한국적 요소는 미확정 디자인 후보 문서에 두고 공간 맥락에 맞게 선택한다.
5. **Fashion Week Backstage:** Runway 없이도 독립적인 소셜/탐험 공간으로 가치가 있는지 검토한다. 포털과 경기 시스템은 미래 범위다.

**완료 조건:** 각 공간에 시각적 특징뿐 아니라 실제 행동이 있고, 이동·카메라·충돌·다중 사용자·성능을 확인했다.

### Stage 7 — 통합 QA와 출시 전 검증

- [ ] 핵심 Catalog/SavedOutfits 흐름을 PC/모바일에서 회귀 테스트한다.
- [ ] 다중 플레이어 가시성, 요청 중복, respawn, 연결 끊김, 저장/복원 오류를 테스트한다.
- [ ] 실제 플레이어 밀도와 성능을 확인한 후 Main Social 인원 수와 장식 수준을 조정한다.
- [ ] 각 기능의 상태를 planned / source-present / user-confirmed / Studio-verified로 분리 기록한다.
- [ ] 테스트하지 않은 항목을 완료로 표시하지 않는다.

### Stage 8 — 미래 후보 재평가

## 3. 서로 다른 두 종류의 제작 순서

- **게임 전체 개발 순서:** 이 문서와 `ROADMAP.md`에서 관리한다. 어떤 시스템/경험을 먼저 완성할지, 무엇이 무엇에 의존하는지를 뜻한다.
- **공간 내부 제작 순서:** 각 공간 문서의 “공간 제작 순서”에서 관리한다. 블록아웃→동선/카메라 검증→핵심 상호작용→다중 사용자 검증→아트 폴리시처럼 해당 공간을 어떻게 만들지 뜻한다.

공간 블록아웃을 일찍 진행한다는 것은 모든 공간의 상세 모델링/상호작용 구현을 앞당긴다는 뜻이 아니다. 핵심 카탈로그 시스템을 검증하면서 맵의 크기와 연결만 저비용으로 확인하고, 이후 한 공간씩 완성한다.
